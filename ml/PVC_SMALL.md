# A small PVC model for the device — chosen on DS1, tested on DS2 (Notebook 13)

Kaggle notebook `bekturasilov/afib-small-pvc-model-ds1-ds2`, version 2 (18 Oct 2026). The cell runs the code of
`ml/pvc_small.ipynb` byte for byte (sha256 prefix `af65db60635ae88a`), which includes `backend/app/ectopy.py`
(the same features the server and the device compute). Version 1 stopped before any result: the module looked for
its model file with `__file__`, which does not exist inside a notebook. Fixed in 29ab55d, rules unchanged.

**Rules fixed before the run** (33f73b0):
* Task: ventricular ectopic beat (V, E) vs any other beat. Split: DS1 / DS2 of de Chazal et al. 2004, paced records out.
* Candidates: (A) 50 trees, depth ≤ 3; (B) 100 trees, depth ≤ 4; (C) logistic regression.
* Choice: best V F1 in 5-fold GroupKFold over DS1 records. DS2 is not used for the choice. Threshold 0.5.

## Choice on DS1 (cross-validation, other people in each fold)

| Candidate | V F1 | Sensitivity | PPV |
|---|---|---|---|
| A — 50 trees, depth 3 | 0.755 | 94.6 % | 62.8 % |
| **B — 100 trees, depth 4** | **0.830** | **92.8 %** | **75.1 %** |
| C — logistic | 0.475 | 84.5 % | 33.0 % |

B is chosen.

## Test on DS2 (22 other people, beats of our own R-peak detector)

| Candidate | V F1 | Sensitivity | PPV |
|---|---|---|---|
| A | 0.906 | 95.9 % | 85.9 % |
| **B (chosen)** | **0.922** | **95.4 %** | **89.1 %** |
| C | 0.780 | 88.2 % | 70.0 % |

For comparison, Notebook 11's 300-tree model gave 94.7 % / 91.8 %. The 100-tree model loses about 3 points of PPV.

**Per record:**
* The PVC burden found vs labelled has a Spearman correlation of 0.82.
* All 5 records with ≥ 10 % PVC (200, 214, 221, 228, 233) were found, with no false ones at that level.
* Errors that remain:
  * 232 (sinus bradycardia with long pauses, 0 labelled V): 145 beats, 8.2 %, called PVC.
  * 105 (very noisy): 108 counted vs 41 labelled.
  * 228: 285 counted vs 361.

## Export and parity
* **Exported model vs sklearn on the notebook's own beats:** max probability difference 0.0, with the same decision on 48,562 of 48,562 beats.
* **Committed model:** `backend/app/pvc_model.json`, sha256 `f719e22616a9928d`, the same as printed in the log. A test checks this.
* **Device tables:** generated by `tools/pvc_export.py` into `firmware/AFibMonitor/pvc_model.h`: 2,932 nodes, 117 KB of flash.
* **Device code on a PC vs the server**, on 40 strips / 910 beats:
  * same PVC decision on 910 of 910 beats;
  * feature difference 0 and probability difference 0 (bit for bit).

  The first comparison found one beat where they differed. Its mean-RR value lay exactly on a tree threshold: Python 3.12+ `sum()` uses compensated
  summation, while the C++ code added plainly, so the last bit differed and the beat took the other branch
  (p 0.41 vs 0.35). The device now uses the same summation as CPython. The server runs Python 3.12 (Dockerfile).
  CI checks both that the header is generated from the committed model and that the results match bit for bit.
* **On the chip:** after each 30-second check, Serial prints `PVC research beats=… pvc=… calc_us=…`. The time on the chip
  is still to be measured on the bench (BENCH_TEST.md §5).

## Status
Counting PVCs is arrhythmia detection, which is a medical-device claim. Until registration it is shown only in research mode, only
to the doctor, labelled as an estimate (the web strip view, "research" tag). Patients never see it. In wellness mode
it is switched off. The numbers above come from one public database (MIT-BIH, 1980s Holter, 2 leads, our lead =
MLII). How it performs on our chest patch is unknown until a clinical comparison with a cardiologist's annotation.
